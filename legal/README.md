# Подготовка Organizm к работе в РФ

Статус на 17.11.2026: подготовка, а не подтверждение полного соответствия законодательству. Документы в `drafts/` не утверждены, не являются офертой и не должны подключаться к формам как действующие документы.

## Установленные факты

- Проект Supabase `organizm` размещён в `eu-central-1`. В нём находятся профили, SteamID64, контакты, команды и история матчей. Auth, Storage, Edge Functions и резервные копии также требуют отдельной проверки размещения.
- Единственный вход — Steam OpenID. Функция `steam-auth` создаёт аккаунт Supabase и сессию по подтверждению Steam.
- Профили и рейтинги доступны публично; политика `profiles_read` разрешает чтение всех профилей. Отдельного согласия на распространение в коде нет. Изменение только видимости в интерфейсе не закрывает доступ через API.
- Контакты доступны по RLS сокомандникам, организаторам, администраторам и в отдельных сценариях капитанам и приглашённым игрокам.
- В коде нет приёма платежей, но есть пользовательские поля взноса и призов. Реальные денежные отношения необходимо уточнить у владельца.
- До изменений клиент загружал Google Fonts, Supabase SDK с jsDelivr и изображения с адресов, введённых пользователями или полученных из Steam.
- Владелец, адрес, контакт для обращений, правила участия несовершеннолетних, сроки хранения и статус уведомления Роскомнадзора пока не установлены.

## Что подготовлено в этой ветке

SDK той же версии поставляется локально; внешние веб-шрифты убраны; изображения показываются только с origin площадки, иначе используется текстовая/графическая заглушка. Уточнено описание доступа к контактам. Добавлена страница локального хранения с очисткой собственных ключей приложения. Очистка браузера не удаляет аккаунт и не является отзывом согласия.

Эти изменения сокращают лишние внешние обращения, но не локализуют базу, авторизацию или хостинг. Изображения из существующего Supabase Storage также будут заменены заглушками, пока их не перенесут под origin площадки. Не включать произвольные внешние origins ради возврата аватаров.

## Блокирующие решения перед выпуском

| Решение | Что требуется |
|---|---|
| Оператор | ФИО/наименование, статус, адрес, контакт для запросов; реквизиты бизнеса при наличии |
| Размещение | Российские мощности для основной БД, Auth, файлов, журналов и резервных копий; договоры и перечень обработчиков |
| Вход | Выбрать и реализовать допустимый способ; Steam рассматривать как игровую привязку после основного входа, с отдельной оценкой трансграничных операций |
| Публичные данные | Перечень раскрываемых полей, правовое основание; где используется согласие на распространение — отдельные настройки и доказательства получения; защита на уровне API/RLS |
| Обращения | Рабочий канал запросов, подтверждение личности без избыточного сбора, порядок доступа, исправления, прекращения обработки, удаления и отзыва согласия |
| Возраст | Допуск несовершеннолетних и процесс участия законного представителя; не считать обычную галочку проверкой возраста |
| Деньги | Кто принимает взнос и выдаёт приз, условия отмены/возврата, необходимые оферта, чеки и налоговые процедуры; отдельно оценить турниры со взносами, ставки и случайные розыгрыши |
| Уведомления | Проверить обязанность и фактическую подачу уведомления по ст. 22; отдельно проверить ст. 12 при трансграничной передаче |
| Организация защиты | Ответственный, права доступа, учёт инцидентов, восстановление, сроки хранения и уничтожения, договоры с обработчиками |

## Порядок переноса

1. Выбрать инфраструктуру в РФ, проверить фактические места обработки и договоры, включая технические журналы. Один reverse proxy перед иностранной базой не решает локализацию.
2. Развернуть целевую среду. Переносить схему, Auth с сохранением идентификаторов, Storage и необходимые функции как связанную систему.
3. Провести проверку на синтетических данных: вход, соответствие старых пользователей, команды, сетка, пики/баны, Realtime и резервное восстановление.
4. Согласовать короткое окно записи, выполнить контролируемый перенос, проверить целостность и переключить frontend. Не использовать длительную двойную запись в иностранную и российскую базы как обход локализации.
5. Отключить прежние точки обработки по согласованному плану хранения и удаления. Не удалять рабочую базу до проверки переноса и согласования судьбы существующих данных.
6. После заполнения и проверки документов опубликовать политику и сведения об операторе. Отдельные согласия оформлять до соответствующей обработки; хранить версию текста и серверное подтверждение действия пользователя. LocalStorage не является достаточным журналом согласий.
